1. TAREA COMPLETADA: VERSIONADO OPTIMISTA EN CONSULTAS CLINICAS
===============================================================================

PROBLEMA QUE RESOLVIA
------------------------------------------------------------------------------
guardar_consulta_clinica hacia UPDATE de las columnas del payload SIN comprobar
la version. Si dos equipos abrian la misma ficha y ambos guardaban, el ultimo
borraba lo del primero EN SILENCIO. En datos clinicos eso no es aceptable.

QUE SE HIZO
------------------------------------------------------------------------------
Servidor (nueva migracion):
  supabase/migrations/202609240024_versionado_consultas.sql

  - guardar_consulta_clinica_v2(uuid, jsonb, bigint):
      * SELECT ... FOR UPDATE sobre la consulta: serializa dos equipos.
      * Si p_base_version no coincide con sync_version -> error SQLSTATE 40001.
        El despachador aplicar_operaciones ya traduce 40001 a status 'conflict'.
      * Antes de cada edicion inserta la fila anterior completa en
        consultas_clinicas_revisiones. Aunque el cliente no sepa la version,
        lo pisado queda recuperable: NUNCA hay perdida silenciosa.
      * La version nueva la calcula el servidor. Si el payload trae
        sync_version/server_updated_at, se ignoran.
      * Corrige un fallo latente: jsonb_populate_record no aplica DEFAULT, asi
        que el INSERT inyecta sync_version=0, server_updated_at=now() y
        created_at=now() para que una consulta NUEVA no falle por NOT NULL.

  - guardar_consulta_clinica(uuid, jsonb) se conserva como envoltorio que lee
    base_version del payload. Asi crear_venta y aplicar_operaciones NO se
    tocaron (cero riesgo para ventas).

  - Vista public.vista_pacientes_versionada:
      vista_pacientes + sync_version_consulta, con LEFT JOIN y
      security_invoker=on. Si algo no coincide, la fila sigue saliendo sin
      version; jamas oculta historial.

Cliente:
  src/repositorio/consultas.js
      - lee la version conocida de la consulta (fila local o copia
        "remote:<id>" de la cache) y envia base_version en el payload.
      - si no la conoce, envia null: el servidor no compara, pero guarda la
        revision anterior igualmente.

  src/repositorio/base.js
      - consultationPayload elimina sync_version, syncVersion,
        sync_version_consulta y server_updated_at del payload clinico.

  src/repositorio/lectura.js
      - guarda syncVersion al bajar el historial (fila local y cache).

  src/syncEngine.js
      - usa la vista versionada con caida automatica a vista_pacientes.
      - guarda la sync_version que devuelve el servidor tras guardar.
      - reintentarOperacion quita base_version en un conflicto: el reintento
        manual es "guardar mi version" y ya no se queda en bucle. La version
        pisada queda en revisiones.

  src/clasificarFallo.js
      - choque de version -> 'conflict' (nunca 'descartada').
      - mensaje especifico: "no se perdio nada", como recuperar, etc.

Pruebas nuevas:
  src/repositorio/consultasVersion.test.js  (6 casos)
  src/auditoriaSql.test.js                  (bloque 024)
  src/clasificarFallo.test.js               (choque de version)

VERIFICACION
------------------------------------------------------------------------------
  npm test          -> 544 pruebas de logica + 38 de UI, 0 fallos
  npm run lint      -> limpio
  npm run build     -> correcto

ACCION MANUAL PENDIENTE
------------------------------------------------------------------------------

2. TAREA COMPLETADA: TIEMPO REAL (SUPABASE REALTIME)
===============================================================================

PROBLEMA QUE RESOLVIA
------------------------------------------------------------------------------
Los equipos veian los cambios con hasta 30 segundos de retraso (intervalo del
motor de sync). En el mostrador eso significa vender una montura que el
companero ya vendio.

QUE SE HIZO
------------------------------------------------------------------------------
Servidor (nueva migracion):
  supabase/migrations/202609240025_realtime_publicacion.sql

  - Anade a la publicacion supabase_realtime:
      inventario, lista_precios, consultas_clinicas, pedidos_ventas, pagos.
  - Idempotente: comprueba pg_publication_tables antes de anadir.
  - Si el entorno no tiene la publicacion, avisa y sale sin abortar.
  - NO toca datos, RLS ni funciones.
  - No activa replica identity full: solo se usan INSERT/UPDATE. Los DELETE
    siguen cubiertos por el sondeo de 30 s.

Cliente:
  src/tiempoReal.js  (nuevo)
      - Canal 'vermas-cambios' con postgres_changes sobre las 5 tablas.
      - Agrupa rafagas ~350 ms: una venta emite pedido + pago + consulta y no
        se hacen tres descargas.
      - inventario/lista_precios: se aplican con cacheServerCatalog (mismas
        reglas que la sincronizacion normal).
      - consultas/ventas/pagos: trae UNA fila de la vista y la aplica con
        aplicarFilaHistorialRemota. No descarga el historial completo.
      - Los DELETE no inventan borrados locales.
      - Cualquier fallo se registra y se ignora: el sondeo de 30 s corrige.
      - El canal se cierra en detenerTiempoReal (logout / desmontaje).

  src/repositorio/vistaHistorial.js  (nuevo)
      - Centraliza el acceso a la vista de historial con caida automatica
        versionada -> clasica. Lo usan syncEngine y tiempoReal.

  src/repositorio/lectura.js
      - aplicarFilaHistorialImpl(row): aplica UNA fila del historial.
        Garantias:
          * no pisa filas locales con syncStatus 'pending';
          * no retrocede a una version anterior (eventos desordenados);
          * respeta cedulas archivadas y no revive consultas archivadas;
          * actualiza paciente, consulta, venta y copia remota.

  src/localRepository.js
      - aplicarFilaHistorialRemota: pasa por la cola de escritura (prioridad
        baja) para no adelantarse a un guardado local a medio terminar.

  src/hooks/useSincronizacion.js
      - abre el canal al iniciar sesion y lo cierra al salir.
      - NO lo abre en modo PIN local (sin token de Supabase).
      - alCambiar -> obtenerDatos({ sync: false }): relee IndexedDB y repinta.

  src/useGestor.js
      - pasa obtenerDatos y modoSinConexion al hook de sincronizacion.

------------------------------------------------------------------------------

  2. Equipo A: editar el stock de un producto.
     Equipo B: debe ver el stock nuevo en 1-3 segundos, sin recargar.

     debe guardarse en local y subir al reconectar. Realtime no interviene.

4. TAREA COMPLETADA: MANTENIMIENTO DEL ALMACENAMIENTO (#4)
===============================================================================

PROBLEMA QUE RESOLVIA
------------------------------------------------------------------------------
La app guarda todo en IndexedDB. Con el uso diario crece sin limite:
  - los comprobantes y fotos quedaban para siempre, aunque ya estuvieran
    subidos a Supabase Storage;
  - el historial se guardaba DOS veces: en `consultations` y en
    `cache` ("remote:<id>").
Si IndexedDB se llena, el navegador empieza a rechazar escrituras (sobre todo
en iOS) y la app deja de guardar sin conexion. Es el fallo mas grave posible
en una app offline-first.

QUE SE HIZO
------------------------------------------------------------------------------
- src/repositorio/mantenimiento.js (nuevo)
    * purgarAdjuntosSubidosImpl: libera el Blob de los adjuntos con
      status 'uploaded' y mas viejos que 30 dias. Conserva la fila (ruta,
      estado, refId): el binario ya esta en el servidor.
      NUNCA toca 'pending' ni 'failed': pueden ser la unica copia.
    * purgarCacheRedundanteImpl: borra filas de cache de historial con mas de
      90 dias SOLO si la consulta existe en `consultations` como 'synced'.
      Si el dato solo vive en la cache, se conserva.
    * ejecutarMantenimientoImpl: corre como maximo una vez al dia y guarda
      un resumen en meta (mantenimientoUltimo / mantenimientoUltimoResumen).
    * revisarEspacioImpl: uso/cuota/porcentaje reales del navegador.
    * No borra pacientes, consultas, ventas, pagos, inventario ni la cola.

- src/localRepository.js
    * ejecutarMantenimiento (por la cola de escritura, prioridad baja)
      y revisarEspacio.

- src/syncEngine.js
    * Tras el pull: mantenimientoDiario(), siempre protegido con try/catch.
      Un fallo de limpieza no puede tumbar la sincronizacion.
    * status.almacenamiento = { usado, cuota, porcentaje, nivel }.
    * Aviso al 80 % de cuota, como maximo UNA vez al dia (meta
      avisoCuotaUltimo) para que no se convierta en ruido.

- src/PanelSincronizacion.jsx
    * Muestra "Almacenamiento del equipo: X % usado" y, si pasa del 80 %,
      indica donde liberar espacio.

Pruebas nuevas:
  src/repositorio/mantenimiento.test.js  (6 casos reales sobre IndexedDB)
  src/almacenamiento.test.js             (8 casos de contrato)

VERIFICACION

  npm run lint               -> limpio
  npm run build              -> correcto
  npm run verificar:tamano   -> OK (189.1 / 220 kB y 244.1 / 400 kB)

NOTAS
------------------------------------------------------------------------------
  - Las retenciones se pueden ajustar en mantenimiento.js:
      DIAS_ADJUNTOS_SUBIDOS = 30
      DIAS_CACHE_REDUNDANTE = 90
    Subirlas consume mas espacio; bajarlas libera antes pero reduce lo
    disponible sin conexion.
  - Los adjuntos liberados siguen viendose online (URL firmada de Supabase).
    Sin internet y con mas de 30 dias, el comprobante no estara en el equipo.
    Es el compromiso razonable para no llenar el disco.

    incluye el binario y no falla.

         * vista_pacientes y vista_pacientes_versionada.
     - No reproduce RLS, triggers, storage real ni Realtime: no hacen falta
       para estos escenarios.

  2. Apoyo de las pruebas (e2e/apoyo.js)
     - abrirEquipo(): contexto de navegador aislado (localStorage + IndexedDB
       propios) con una sesion ya inyectada, para no repetir el login.
     - Intercepta todas las llamadas a *.supabase.co y las manda al servidor

       guardarConsulta, guardarVenta, sincronizar, leerOutbox, leerConsulta,
       leerInventario, leerVenta.

  3. Escenarios (e2e/dos-equipos.spec.js)
     - Sin internet: guardar una consulta, verla en la cola como pending,
       reconectar y comprobar que sube y queda synced.
     - Misma consulta: A edita y sube (version 2); B edita sobre la version 1.
       B recibe conflict con el mensaje "modificada en otro dispositivo",
       conserva su edicion local y el servidor mantiene la de A.
     - Mismo stock: A vende la unica unidad; B vende la misma. El servidor
       rechaza a B con "stock insuficiente" (conflict), el stock no queda
       negativo y la venta/consulta de B siguen en el dispositivo.
     - Frescura: A guarda y B solo sincroniza; B ve el cambio sin recargar.

  4. CI (.github/workflows/ci.yml)
     - Job `e2e` aparte: npm ci, instala Chromium y ejecuta `npm run test:e2e`.
     - Si falla, publica playwright-report como artefacto (7 dias).

  5. Bug real encontrado y corregido (src/repositorio/ventas.js)
     - Al vender desde una consulta ya existente, guardarVentaLocal hacia un
       put de una fila minima: borraba del dispositivo la evaluacion clinica y
       las medidas, y la dejaba marcada como pending sin ninguna operacion que
       la volviera a subir. El pull tampoco la recuperaba.
     - Ahora solo crea la consulta si de verdad no existe; si existe, no la
       toca. Regresion cubierta en src/repositorio/ventas.test.js.
